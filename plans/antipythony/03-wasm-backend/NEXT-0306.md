## Increment 2 (d1b81f8) — browser smoke demo: decision + VERIFIED result

**Engine decision (recorded per the leaf brief):** wasmtime does not run in
browsers — there is no wasm32-unknown-unknown wasmtime build (option (a) of
the brief: rejected). Chosen: option (b) — the ap-codegen-wasm-emitted
module runs DIRECTLY on the browser's native WasmGC + exception-handling +
tail-call support through a ~60-line JS shim providing the module's 3
imports. Option (c) (Node smoke) unnecessary — (b) worked.

The module imports (verified by binary-parse of the emitted modules):
- `wasi_snapshot_preview1.fd_write (i32,i32,i32,i32) -> i32` — JS shim reads
  the iovecs out of the EXPORTED `memory`, decodes, appends to the DOM log,
  writes nwritten. No WASI implementation needed for this slice.
- `aprt.abort_msg (anyref)` — logged as the internal-error path (never fires
  on these cases).
- `wasi_snapshot_preview1.proc_exit (i32)` — JS shim throws a sentinel
  object; `_start`'s rc is recovered from it.
The demo does NOT need the full aprt host: no corpus case in the demo slice
calls now_ns/wall_ns, and fd_write/proc_exit cover the rest. Satisfiable
in-browser, exactly as the brief allowed.

`examples/browser-smoke/index.html`: ONE self-contained file (~100KB) — the
three embedded base64 blobs ARE the exact bytes ap-host runs (hello,
GE001-yield-next-exhaust, CLW001-init-attr-store; dumped by cli_corpus_dump).
Same bytes, different engine — the .wasm stays the contract under test.

**VERIFIED 2026-11-18 (real browser run, not simulated):** Chrome
157.0.8103.79 headless (macOS aarch64, driven over CDP):
- all three modules COMPILE (WasmGC + EH + tail-calls decode and validate);
- hello → `hello, wasm`, rc 0;
- GE001 → the FULL pin byte-exact (0/1/2/exhausted/v 0/v 1/1 2/x/1/
  after-close — close-before-start, send, throw-in-gen exhaustion all
  behave), rc 0;
- CLW001 → `5\n7\n` byte-exact vs the pin, rc 0.
GOTCHA: wasm-encoder 0.263's `TypeSection` uses `types.ty().function(...)`
(not `types.function`), and the import section of these modules is exactly
3 entries — never more — so the JS importObject is tiny and stable.
KNOWN LIMITATION (honest): Firefox 129+ should also work (GC+EH+tail-calls
stable there) but was NOT verified on this machine; the demo page says so.

## Increment 3 (1f85999) — wasi-threads feasibility spike (probe, NOT a gate)

`crates/ap-codegen-wasm/tests/thread_spike.rs` (`cargo test -p
ap-codegen-wasm --test thread_spike -- --nocapture` prints the evidence):

1. **`Config::wasm_threads(true)` EXISTS and WORKS in wasmtime 47**: an
   engine built with it compiles a shared-memory module
   (`shared: true`, min=max=1) — core wasm threads is fully present. The
   "wasmtime removed wasi-threads" note (design §9, PROGRESS.md) is
   precisely scoped: what was REMOVED is the wasi-threads PROPOSAL layer,
   not the threads proposal.
2. **wasmtime-wasi 47 ships NO `wasi_thread_spawn` host binding** (grep
   over the crate source: 0 matches). Spawning would be OUR embedding code:
   `Linker::func_wrap("wasi_snapshot_preview1", "wasi_thread_spawn")` +
   `std::thread::spawn` handing each spawned instance its tid — i.e.
   building wasi-threads ourselves on top of core threads. Feasible but
   real work; the shared-everything-threads proposal remains the
   standard-track alternative (browser-side too).
3. **Production behavior unchanged**: the same shared-memory bytes through
   `ap_host::run` hit the leaf-03.05 surface check and are refused BEFORE
   compile with `HostError::Threading` carrying the design-§9 diagnostic
   (captured verbatim in the probe output).
4. **Feasibility verdict for the master-contract note**: Plan 03 v1 stays
   single-threaded (locked); if threading is ever wanted in wasm mode, the
   path is core-wasm-threads + a home-grown spawn binding in ap-host (or
   shared-everything-threads when it lands) — NOT a wasmtime upgrade,
   because the missing piece is the WASI shim layer, not engine threads.

GOTCHA that cost real time (recorded for the next wasm probe author):
wasmtime 47 refuses modules whose memory declares a non-default
`page_size_log2` unless custom-page-sizes is enabled — the symptom is a
flat "failed to parse WebAssembly module" on ALL variants while wasmparser
VALIDATES them and wasmprinter prints them. The toy probe originally set
`page_size_log2: Some(16)`; `None` fixed it. Diagnostic order that cracked
it: (a) same bytes through `wasmtime::Module::new` on both engines, (b)
`wasmparser::Validator` with threads on, (c) a KNOWN-GOOD control module
(hello.wasm) on the same API to prove the engine works, (d) feature-by-
feature diff vs the working module.
