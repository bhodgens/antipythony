# Leaf 03.06 — Browser smoke + threading spike

## Source
plans/antipythany/03-wasm-backend/orchestrator.md §03.06 (last leaf;
feasibility probe, NOT a pass/fail gate). Context: design doc §9
(wasmtime 47 removed wasi-threads, #13558 — the spike evaluates

## Scope
1. Browser smoke: ONE HTML demo embedding a wasm-mode runner executing a
   corpus script (hello-world + one generator + one class script). Engine
   decision recorded IN THIS LEAF (orchestrator: "wasmtime browser build
   or documented alternative — decision recorded in the leaf"): candidates
   are (a) compile ap-host to wasm32-unknown-unknown (wasmtime in the
   browser is not a supported target — likely rejected, record why),
   (b) run the ap-codegen-wasm-emitted module DIRECTLY in the browser on
   its native WasmGC+EH support with a tiny JS shim providing the WASI
   fd_write/aprt imports, (c) a Node-based smoke as the documented
   fallback. The emitted .wasm itself is the contract under test — the
   demo must load the SAME bytes ap-host loads.
2. wasi-threads → shared-everything-threads spike: attempt the corpus
   threading slice under ap-host with thread support on (wasmtime 47
   experimental; check availability on the dev platform). Document the
   result either way: what ran, what trapped, what the single-threaded
   diagnostic path did. Output feeds the master-contract
   target-dependent-guarantee note (orchestrator Design §Threading).
3. Report: one page in the leaf report — engine decision + rationale,
   threading spike result, follow-up items (spec 07 gap-list additions
   if any).
